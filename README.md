# mini-framework

A minimal, schema-driven CRUD framework built around seven essentials:

1. `fn.element.create` -- the one DOM-builder primitive everything else is built from.
2. `fn.component.layout.set/get/create` -- a named-layout registry/dispatcher.
3. `fn.data.select/insert/update/delete` -- a CRUD abstraction (localStorage-backed here; swapping the storage layer only means rewriting these four functions).
4. Schema-driven `form`/`list` layouts -- a `resource: {key, columns}` shape plus `data`/`datas` mechanically drives a full CRUD UI, no per-resource UI code. `list` pages itself past `opt.pageSize` rows (default 10), paired with a `pagination` layout that finds its own `list` via `.closest('.__list')` rather than a caller-injected callback.
5. A `render` escape hatch -- a column can carry a JS source string instead of a fixed type, letting a resource definition (pure data) extend what a field/cell does without touching this file.
6. A resource-reference field (`column.form.resource: {key, label}`) -- a select whose options come from another resource's rows, auto-resolved to a label everywhere it's displayed.
7. The `opt` single-parameter convention, and self-contained components that find their own context via `.closest('.__popup')` / `.querySelector('.__form')` instead of caller-injected callbacks.

No build step, no dependencies. The framework is one file, `fn.js` (essentials #1-3, #5) --
essentials #4, #6, #7 are conventions (schema-driven `form`/`list`, resource-reference selects,
`opt`-based self-contained components) that every app implements for itself, the same shape each
time. `fn.component.layout.js`, also at the repo root, is a reference implementation of
`popup`/`close-btn`/`save-btn`/`form`/`list`/`pagination` built that way -- not a dependency any
example currently loads, kept here for later use. `fn.util.js` is different: it's plain CRUD/UI
logic (`fn.util.selectFlat`, `fn.util.newButton`, `fn.util.saveForm`, `fn.util.route`) that has no
reason to vary between examples the way `popup`'s look does, so every example does load it,
rather than re-typing the same logic into its own `app.js`/`layout.js`.

## Design history

This framework's shape was validated against two throwaway example apps -- a floating-popup task tracker (Projects + Tasks) and a multi-page recipe site using hash routing (Categories + Recipes) -- before both were removed once they'd done their job. Three real gaps they surfaced are still reflected in the code today:

- The `form` layout had no `textarea` support at all (only text input, select, and the render escape hatch) -- fixed by adding the `textarea` form type.
- `list`'s row-click always opened its edit popup with `caller: e.target.closest('.__popup')`, so a list embedded directly in a page (not inside a popup) had no way to get refreshed after an edit -- fixed by letting an explicit `caller` passed to `list` win over the auto-detected one.
- Every popup's/page's own `.refresh()` had to hand-clear its container's children before recreating the list inside it, reaching past `fn.component.create` into raw DOM (`.children`, `.remove()`) -- fixed by adding `fn.component.refresh`, so `.refresh()` implementations only ever call back into the framework.
- `list` had no way to page through a resource with more than a handful of rows -- fixed by adding a `pagination` layout paired with `list` (list slices its own `datas` by `opt.pageSize` and keeps the current page on its own `.__list` wrapper; `pagination`'s Prev/Next buttons find that wrapper via `.closest('.__list')`, the same self-contained convention `close-btn`/`save-btn` already used, instead of `list` handing them a callback).
- Once three examples existed, the same CRUD logic (a `save-btn`'s insert-or-update-then-refresh, the "+ New X" button that opens a blank form, and `fn.data.select(...).map(...)` flattened into `{id, ...data}`) was typed out nearly verbatim in each one -- a real, not hypothetical, duplication that had already caused a bug (a stringified `"undefined"` `disabled` attribute, copy-adjusted wrong in one of the three copies). Fixed by adding `fn.util.js`: unlike `fn.component.layout.js`, this one every example does load, since none of this logic has a reason to differ by theme the way `popup`'s look does. The insert-or-update part specifically moved one level further, from `fn.util.saveForm` into `form.save()` itself -- swapping storage backends may need per-resource save behavior someday (see "Known limitation" below), and the form (which already owns its resource and data) is where that belongs, not a generic shared helper.
- `crm/` hand-wrote its own 'router' layout (read `location.hash`, look it up in a routes map, refresh the matching layout, redo it on every `hashchange`) so its tab bar's browser back button would work, and for a long time stayed the only example that needed it -- the other examples' single always-on shells, tab-swaps, and screen-stacks genuinely didn't need a URL to name what they were showing. That changed once real per-tab/per-channel navigation elsewhere needed the exact same read-hash/resolve-a-layout-name/refresh-on-hashchange mechanism, just resolving a variable key instead of picking from two fixed pages -- a second, real use of code that was, until then, one example's own. Fixed by adding `fn.util.route`, generalized just enough to cover both shapes (`opt.routes`, a fixed hash-to-layout map, for a small fixed screen set; `opt.resolve(hash)`, a function, for a hash carrying a variable id/key) without forcing either shape to bend to fit the other.

## Using it

Load `fn.js` as a plain `<script>` tag before your app's own script(s) -- it attaches to the global `fn` object, no build step needed. `fn.js` alone doesn't give you `popup`/`form`/`list`/etc. -- write your own `layout.js` registering the ones you need (see any example folder), or start from `fn.component.layout.js` as a reference. `fn.util.js` (load it after `fn.js`, before your `layout.js`/`app.js`) has `fn.util.selectFlat`/`fn.util.newButton`/`fn.util.saveForm`/`fn.util.route` -- optional, but every current example uses it rather than re-implementing the same CRUD wiring.

## Examples

`index.html` at the repo root lists every example app, each in its own folder next to it. Open it (serve the directory, e.g. `npx serve .`) to browse them:

- `crm/` -- Contacts + Deals, mobile-oriented (bottom tab bar, full-width touch-sized buttons), with Deals referencing both a Contact and a Stage (Stage is itself a seeded resource, so a fixed set of choices needs no framework change). Its `layout.js` defines mobile-appropriate `popup`/`close-btn`/`save-btn`/`form` (full-screen modal instead of a small fixed-position box, 16px inputs, bigger tap targets) plus `list`/`pagination` unchanged from `fn.component.layout.js`'s reference implementation. Which page (Contacts vs Deals) is showing is a real route, via `fn.util.route({routes: {'#/': 'contacts-page', '#/deals': 'deals-page'}, ...})` -- the tab bar's `<a href="#...">` links are real navigations, so the back button steps back through pages instead of leaving the app; only the edit/new popups stay unrouted, the same as everywhere else.
- `windows-os/` -- a Folders + Files file manager (Files referencing a Folder), styled as a Windows-OS-style desktop: draggable/resizable/minimizable/maximizable windows, a taskbar with running-window buttons and a clock, and a Start menu, all in `layout.js`. `popup`/`close-btn`/`save-btn` plus new app-only layouts (`desktop`, `taskbar`, `taskbar-windows`, `clock`, `start-menu`, `desktop-icon`, `minimize-btn`, `maximize-btn`) are Windows-OS-styled; `form`/`list`/`pagination` are unchanged from the reference implementation. Exactly the UI chrome CLAUDE.md calls out of scope for the framework itself (popup dragging/resizing, z-index, cascading position). Deliberately not hash-routed like the other four: any number of windows can be open and overlapping at once, so there's no single "current screen" for a URL to name -- routing assumes exactly the one-screen-at-a-time shape this app's whole point is to not have.
- `android-phone/` -- Contacts + Notes (Notes referencing a Contact), styled as an Android phone screen filling the whole viewport (no device bezel -- a status bar, a home screen of tappable icons, full-screen app views, and a 3-button nav bar (Back/Home/Recents) with real back-stack navigation), all in `layout.js`. Same shape again (`popup`/`close-btn`/`save-btn` plus `phone`/`home-screen`/`app-icon`/`nav-bar`/`status-clock` themed, `form`/`list`/`pagination` unchanged); `close-btn` becomes the in-app-bar back arrow, and both it and the nav bar's Back button pop the same screen stack. Which app is open (Home/Contacts/Notes) is also a real route ('#/app/<key>'), but through a plain hand-rolled `hashchange` listener instead of `fn.util.route`: that helper's contract is "wipe the container and render one named layout," which fits every other example's single current screen but not this one's layered stack (a persistent home screen underneath, with any edit/new popups stacked on top of the open app) -- so the physical back button and the nav bar's Home/Recents buttons both close a whole app at once, same as Home always did, rather than trying to replicate the in-app back arrow's one-screen-at-a-time pop.
- `team-chat/` -- Channels + Messages (Messages referencing a Channel), styled as a Slack-style messenger with a persistent split-pane chrome: a sidebar of channels and the selected channel's messages are both on screen at once, unlike the other three examples' one-screen-at-a-time chrome (tab swap, window stack, screen stack). Clicking a channel doesn't open a popup -- it's a real route (`fn.util.route` resolving `'#/channel/<id>'`) into the main panel, so the sidebar itself never decides what to show; it's a fixed shell around whatever the route renders, and the back button steps back through channels you've visited. This example writes its own `sidebar`/`channel-item`/`main-panel` layouts instead of using `list`/`pagination` at all (neither is defined). Messages never go through the schema-driven `form`/`list` either -- a dedicated `composer` layout inserts them directly, since a chat compose box doesn't fit the modal-edit-form shape; only Channel is CRUD'd through the usual `popup`/`form`/`save-btn` (the "+ New Channel" button and each channel's edit icon).
- `idle-hunter/` -- Player + Ground + HuntLog, a dark-fantasy idle RPG rather than a CRUD app. The player has no level/XP -- just Attack, Defense, and HP, all derived purely from weapon/armor level and moved only by buying a Shop upgrade. A `<select>` (no `list`/`pagination` needed -- Ground is only ever entered, never edited) plus an Enter button picks one of 10 seeded Ground rows with difficulty scaling by `huntLevel`; entering starts a `setInterval` that resolves real combat unattended: the player's Attack damages a persistent per-encounter monster HP pool (killing it drops Iron Ore + gold and spawns the next one), and a surviving monster hits back for real damage against the player's own HP, until Stop Hunting clears the interval -- the only thing that does. Potions are never a manual reflex: the instant a hit would leave the player at or below a set fraction of max HP, one auto-drinks itself (a manual Use Potion button on the stat bar exists too, for topping off before a hunt) -- with none left, the player is defeated and forced back to town. Iron Ore is inert until either sold directly or combined (the Bag tab, a chosen quantity at once via a number input plus a Max button) into a higher-value Iron Ingot, so "hunt for ore -> combine -> sell -> upgrade -> hunt harder ground" is a real loop. `town` is the single persistent shell -- stat bar, a shared `feed-box` (a bordered text box of the most recent HuntLog activity), tab content, then the bottom tab bar (Hunt/Bag/Shop/Log) -- and it's the only thing ever re-rendered, whether or not a hunt is in progress: `hunt-tab` itself branches on whether a ground is active to show either the picker or the live encounter, so the tab bar and stat bar never disappear mid-hunt the way a separate full-screen "hunting" layout would make them. Which tab is active is a real route, via `fn.util.route` (`'#/hunt'`/`'#/bag'`/`'#/shop'`/`'#/log'`, defaulting to Hunt) -- tapping a tab is a real navigation, so the back button steps back through tabs instead of leaving the app; `activeGroundId` itself stays a plain module var, since which ground you're hunting (or mid-hunt at all) isn't a distinct screen, just state the Hunt tab's own render branches on. HuntLog is a growing resource genuinely worth paging through (`list`/`pagination`, restyled compact so a page fits without scrolling); Player is CRUD'd through the usual `popup`/`form`/`save-btn` only for its name (the Rename button) -- gold/ore/ingots/hp/weapon level/armor level/potions are game state a form should never expose directly.

Every example defines every layout it needs (`popup`/`close-btn`/`save-btn`/`form` at minimum, plus `list`/`pagination` where used) in its own `layout.js`, loaded right after `fn.util.js` and before `app.js` -- none of them load `fn.component.layout.js`, which is itself just a reference implementation of those same layouts, not a framework dependency (see "Example folder structure" in CLAUDE.md). All five do load `fn.util.js`: `save-btn` calls `fn.util.saveForm`, which calls the popup's `.__form`'s own `.save()` (insert-or-update, defined identically in every example's `form` layout) and then refreshes the caller, passing only how that example's chrome closes (`popup.remove()` in `crm/`/`team-chat/`/`idle-hunter/`, `closeWindow` in `windows-os/`, `popScreen` in `android-phone/`); `app.js`/`layout.js`'s resource-list-fetching goes through `fn.util.selectFlat` everywhere, and every "add new X" button goes through `fn.util.newButton` (`idle-hunter/`'s Rename button doesn't -- it edits the existing Player row rather than adding one, so it opens its own popup+form by hand) instead of each defining its own. Three of the five -- `crm/`, `team-chat/`, `idle-hunter/` -- also call `fn.util.route`, each giving it either a fixed `routes` map or a `resolve` function depending on whether its screens are a small fixed set or keyed by a variable id; `android-phone/` routes too but through its own hand-rolled `hashchange` listener instead (see its bullet above for why), and `windows-os/` doesn't route at all.

## Known limitation: swapping to a real network backend isn't free

Essential #3 above claims that swapping the storage layer only means rewriting `fn.data.select/insert/update/delete`. Verified against a real local HTTP server, that claim holds *only* because those four functions can stay synchronous (using synchronous XHR to keep the exact same call-and-get-a-return-value shape localStorage has) -- no other file needed a single change.

A real production backend would use `fetch`/Promises instead, which means `fn.data.*` would have to become async -- and every place that currently does `var rows = fn.data.select(...)` and uses `rows` immediately (throughout `list`/`form`, and every app built on them) would need to change too. That ripple is real work, and deliberately not done speculatively: the right async shape (loading states, error handling, what a popup does mid-save) can only be designed against a real backend that needs it, not guessed at in the abstract. See "Adding to the framework" in CLAUDE.md -- this is the same principle, applied to a foundational shape instead of a single feature.
